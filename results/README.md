# 결과

분류 방식별 비교. 전부 같은 골든셋 **198건**을 `src/evaluate.py`로 평가한 값이다.

**골든셋**: 자동차 리뷰 영상 5개에서 후보 260건을 뽑아 수작업 라벨링, 제외 72건(27.7%) → 198건.
분포는 긍정 82 (41.4%) / 부정 52 (26.3%) / 복합 64 (32.3%).

| 방법 | macro F1 | 정확도 | 학습 | 비고 |
| --- | --- | --- | --- | --- |
| 다수 클래스 | 0.195 | 0.414 | 없음 | 전부 '긍정'. 하한선 |
| 어휘 규칙 | 0.285 | 0.404 | 없음 | `lexicon.py` |
| **TF-IDF + 로지스틱 회귀** | **0.334** | 0.404 | 154건 | `embed_classifier.py` |
| LLM zero-shot | | | 없음 | 미실시 — API 크레딧 필요 |
| 오픈모델 + LoRA | | | 154건 | 미실시 |

측정일 2026-08-09. 골든셋 **198건**, 학습셋 **154건**, 겹침 0건.

> 처음엔 골든셋 247건 / 학습셋 210건이었다. 측정을 끝낸 뒤 라벨 노이즈를 발견해 양쪽을 정제했다 — 아래 "평가셋을 다시 만든 이야기" 참조.

## 읽을 만한 것 세 가지

### 1. 정확도는 세 방법이 거의 같은데 macro F1은 1.7배 벌어진다

다수 클래스가 정확도 0.414로 **가장 높다.** 아무것도 학습하지 않고 전부 '긍정'이라고 찍은 결과다. 반면 macro F1은 0.195로 셋 중 꼴찌다.

TF-IDF는 정확도가 0.404로 오히려 낮은데 macro F1은 0.334다. 긍정을 조금 덜 맞히는 대신 부정과 복합을 잡기 시작했기 때문이다. **정확도만 봤다면 아무것도 안 하는 쪽을 골랐을 것이다.**

### 2. 클래스 가중치 하나가 macro F1을 0.194 → 0.334로 올렸다

처음 설정(`char_wb(1,3)`, `min_df=2`, 가중치 없음)은 198건 중 **197건을 긍정으로 찍었다.** 부정과 복합은 한 건도 못 맞혔다.

```
          긍정   부정   복합
긍정      81     1     0
부정      52     0     0
복합      64     0     0
```

macro F1 0.194 — **아무것도 학습하지 않은 다수 클래스(0.195)보다 낮다.** 학습셋의 긍정 비중이 51.9%라 분류기가 다수 클래스로 수렴했고, 무의미한 예측 한 건 때문에 오히려 손해를 봤다.

`class_weight="balanced"`를 넣자 예측이 세 클래스로 흩어졌다.

```
          긍정   부정   복합
긍정      59    12    11
부정      35     7    10
복합      44     6    14
```

설정은 **학습셋 내부 5-fold 교차검증**으로 골랐다. 골든셋은 최종 평가 때 한 번만 봤다.

| 설정 | CV macro F1 |
| --- | --- |
| char_wb(1,3) min_df=2 | 0.226 |
| char_wb(2,4) min_df=1 | 0.229 |
| **char_wb(2,4) min_df=1 + class_weight** | **0.282** ← 채택 |
| char_wb(2,5) min_df=1 + class_weight + C=5 | 0.273 |
| word(1,2) min_df=1 + class_weight | 0.273 |

### 3. 댓글의 61.6%에는 감정 어휘가 아예 없다

어휘 규칙이 198건 중 **122건에서 아무 단어도 못 잡았다.** "기대만큼은 아니지만 나쁘지 않았어요" 같은 문장이 그렇다 — 감정은 분명한데 사전에 있을 법한 단어가 없다.

평가 대상이 아닌 댓글을 걷어낸 뒤에도 61.6%다. 질문 때문이 아니라 **한국어 댓글의 감정이 원래 어휘에 얹혀 있지 않다는 뜻**이고, 이게 어휘 규칙이 0.285에서 멈추는 이유이자 통계 모델이나 LLM이 필요한 이유의 구체적인 형태다.

## 평가셋을 다시 만든 이야기

세 방법을 다 측정한 뒤에 골든셋을 다시 들여다보다가, 차에 대한 평가가 아닌 댓글이 라벨을 달고 들어와 있는 걸 발견했다.

| 댓글 | 붙어 있던 라벨 |
| --- | --- |
| "또치 감독님 안경 브랜드 궁금합니다 너무 잘 어울려요" | 긍정 |
| "카플레이는 유선으로 사용중이신가요 아니면 무선으로…" | 긍정 |
| "2열 승차감 알려주시는분 왜 없죠??????" | 긍정 |
| "신차라서 장점만 말해야 고객들이 사지 그래야 리뷰하는분들도 돈받고" | 복합 |

리뷰어 얘기, 순수한 질문, 리뷰 산업 비판이다. 감정 단어가 없으니 판단할 게 없고, 그러면 무심코 긍정이 붙는다.

**원인은 라벨링이 아니라 이 문서였다.** 당시 규칙 1은 "평가 대상이 차량이나 **리뷰 영상**이 아니면" 이라고 써 놓고 몇 줄 아래에서 "리뷰어 개인에 대한 평가는 뺀다"고 했다. 스스로 모순이었고, 질문·요청은 아예 언급이 없었다. 규칙을 먼저 고치고 다시 검토했다.

### 세 시점

| 방법 | 정제 전 | 평가셋만 정제 | 양쪽 정제 |
| --- | --- | --- | --- |
| 다수 클래스 | 0.193 | 0.195 | 0.195 |
| 어휘 규칙 | 0.275 | 0.285 | 0.285 |
| TF-IDF + 로지스틱 회귀 | **0.345** | 0.319 | 0.334 |

골든셋 247 → 198건(제외율 27.7%), 학습셋 210 → 154건(26.7%).

### 예상이 빗나갔다

정제하면 점수가 오를 거라고 예상했다. **틀렸다.** TF-IDF는 0.345에서 0.319로 떨어졌고, 학습셋까지 정제해 0.334로 회복했지만 원래 값을 넘지 못했다.

이유는 빠진 댓글의 성격에 있다. 질문처럼 감정이 없는 댓글에는 대체로 긍정이 붙어 있었고, **긍정으로 쏠린 분류기는 그것들을 우연히 맞히고 있었다.** 공짜 정답이 사라지자 점수가 내려간 것이다.

평가셋만 정제했을 때 가장 낮은(0.319) 것도 같은 이유다. 학습셋은 여전히 질문 댓글에서 감정을 배우는데 시험지에서는 그게 빠졌으니, 학습과 평가의 기준이 어긋난 구간이었다.

**그래도 정제된 숫자가 맞는 숫자다.** 0.345에는 "질문을 긍정이라 찍어서 얻은 점수"가 섞여 있었고, 0.334는 차에 대한 평가만으로 잰 값이다. 이 파이프라인이 답하려는 질문이 "이 차가 어땠나"라면 후자가 옳은 자다.

## 한계 — 데이터가 부족하다

교차검증 결과가 그대로 말해준다. **학습셋 안에서조차 macro F1이 0.3을 못 넘었다.** 하이퍼파라미터를 바꿔도 0.22~0.30 안에서만 움직였으니, 튜닝이 아니라 데이터가 모자란 것이다.

학습셋과 골든셋의 클래스 분포도 어긋나 있다.

| | 학습(154) | 골든셋(198) | 차이 |
| --- | --- | --- | --- |
| 긍정 | 51.9% | 41.4% | +10.5%p |
| 부정 | 22.1% | 26.3% | −4.2%p |
| 복합 | 26.0% | 32.3% | −6.3%p |

같은 영상에서 같은 방식으로 뽑았는데 긍정이 10%p 높다. 정제 후에도 이 격차는 남았다. 표본 변동일 수도, 라벨링 기준이 미세하게 이동한 것일 수도 있다. 혼동 행렬에서 여전히 긍정 열로 쏠리는 걸 보면 후자의 영향도 있어 보인다.

**다음에 손댈 곳은 하이퍼파라미터가 아니라 데이터다.** 학습셋을 늘리거나, 라벨링 기준을 다시 맞추거나.

## 보는 법

주 지표는 macro F1. 이 데이터는 긍정이 많고 '복합'이 제일 어려워서, weighted F1은 쉬운 클래스 성적에 가려진다.

다수 클래스 행부터 채운다. 전부 '긍정'이라고 답하는 분류기의 점수다. 이게 없으면 나머지 숫자가 좋은 건지 나쁜 건지 판단할 기준이 없다.

```bash
python3 src/baselines/majority.py data/real/golden.csv > /tmp/majority.csv
python3 src/evaluate.py data/real/golden.csv /tmp/majority.csv
```

이 값은 골든셋의 클래스 분포에 따라 크게 달라진다. 긍정이 몰려 있으면 높게 나오고, 고르면 낮게 나온다. 그래서 **점수와 함께 분포도 적어둔다.** 나중에 "왜 이때는 0.4였지" 하고 헷갈리지 않으려면 필요하다.

비용과 지연도 같이 적는다. 정확도만 보면 항상 큰 모델이 이기는데 실제로는 그렇게 고르지 않는다.

## 기록할 것

실행할 때마다 모델명과 버전, 프롬프트나 하이퍼파라미터, 날짜, 골든셋 버전을 남긴다. 몇 달 뒤에 이 숫자가 어떻게 나온 건지 답할 수 없으면 그 행은 지우는 게 낫다.
